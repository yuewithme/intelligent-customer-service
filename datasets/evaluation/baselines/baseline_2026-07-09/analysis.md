# AI兰花销售助手基线评测结论

## 1. 评测范围

| 项目 | 结果 |
|---|---:|
| 被测系统 | 当前本地 `/api/v1/chat` 完整编排链路 |
| 被测模型 | `dashscope/qwen3.7-plus` |
| 裁判模型 | `dashscope/qwen3.7-plus` |
| 真实单轮题 | 30/30完成评分 |
| 真实多轮题 | 9/10完成评分 |
| 未完成题 | `m08_first_purchase`，系统持续返回502 |
| 边界题 | 15题未运行，系统暂不消费评测`tool_state` |
| 有效评分 | 39题 |

## 2. 核心结果

| 指标 | 结果 |
|---|---:|
| 平均分 | 17.92 |
| 中位数 | 4.00 |
| 严重错误率 | 10.26% |

| 多轮平均分 | 17.56 |
| 0分题 | 18 |

39道有效评分题中：

- 没有题目达到90分。

## 3. 系统行为统计

| 行为 | 题数 |
|---|---:|
| 成功完成端到端请求 | 39 |
| 系统请求失败 | 1 |
| 全程没有文本回复 | 15 |
| 至少一轮转人工 | 18 |

当前系统对于严重苗情、订单、活动或无法匹配的话术场景，较容易进入`human`路由。转人工本身不一定错误，但系统经常返回空`answer`，导致客户没有收到：

- 已受理说明；
- 转人工原因；
- 等待期间可以执行的低风险建议；
- 需要补充的照片、订单或环境信息；
- 后续处理预期。

因此大量题目不是“回答质量较低”，而是“没有可评价的客户可见回复”。

## 4. 表现相对较好的题目

| 题目 | 分数 | 主要表现 |
|---|---:|---|
| `c03_n05_product_recommendation` | 89.0 | 能复述客户需求，准确使用商品快照并说明组合价 |
| `c02_n05_watering` | 74.0 | 能说明浇水不能只按固定天数判断，并覆盖主要排查因素 |
| `c05_n03_live_learning` | 69.25 | 能回应资料和学习需求，没有贬低直播渠道 |

这说明系统并非完全不具备回答能力。在命中合适知识或流程时，能够产出较完整的专业或商品回答。

## 5. 主要能力短板

### 5.1 转人工缺少客户可见回复

直接影响：

- 病害排查；
- 会员政策；
- 活动咨询；
- 商品推荐；
- 订单与物流；
- 多轮销售推进。

建议将“转人工”和“是否回复客户”拆成两个动作：

```text
先生成安全、有限、客户可见的承接回复
↓
再创建人工工单
```

### 5.2 会员与业务政策能力薄弱

`O2 活动与会员政策说明`平均2.76分。

常见表现：

- 直接转人工；
- 没有回答价格、权益或有效期；
- 无法区分已确认政策和待查询政策；
- 没有说明包赔或活动的规则边界。

### 5.3 异议与方案调整能力不足

- `S5 异议处理`平均0分；
- `S6 方案调整`平均4分；
- `S3 方案匹配`平均0分。

系统容易：

- 忽略客户当前异议；
- 重复泛化追问；
- 跳过预算、苗数或物流条件；
- 没有在原方案不合适时形成新方案。

### 5.4 专业判断边界不稳定

系统在部分场景直接转人工，另一些场景又会在信息不足时给出确定诊断。

例如多轮图片题中，图片信息不足时直接判断软腐病，触发严重错误。需要统一以下策略：

```text
信息充分 → 提供有依据的初步判断
信息不足 → 明确不确定性并追问
风险较高 → 提供低风险临时措施并转专家
```

### 5.5 多轮流程无法稳定推进

多轮平均17.56分，中位数10分。

主要表现：

- 中途转人工后对话终止；
- 忘记已提供的地区、预算和品种；
- 重复询问；
- 没有从探询进入方案；
- 没有从购买意向进入订单核验和售后。

## 6. 工程可靠性问题

首次运行40题中有7题系统失败，降低并发重试后缩减至1题。唯一剩余失败：

- `m08_first_purchase`：系统返回502。

这说明模型或编排链路在并发情况下存在稳定性问题。后续应记录：

- 具体失败阶段；
- 供应商返回码；
- 重试次数；
- 每个内部模型调用耗时；
- 是否发生JSON解析失败。

当前执行器中的`latency_ms`包含并发信号量排队时间，不等于纯接口处理时间，本次不对性能数据下结论。

## 7. 结果限制

### 7.1 同模型裁判

被测模型和裁判模型均为`qwen3.7-plus`，可能存在同源偏差。本次分数适合作为工程基线，不应直接作为最终验收结论。

建议人工复核：

- 全部3道60分以上题；
- 全部严重错误题；
- 随机抽取5道0分转人工题；
- 随机抽取5道1—59分题。

### 7.2 单轮上下文适配

现有API不支持直接注入系统历史，单轮题通过“已知对话背景＋客户当前消息”的文本封装调用。该方式测试了当前端到端系统对上下文文本的处理，但与真实会话记忆并不完全相同。

### 7.3 边界题未执行

15道库存、活动、订单、支付、退款和隐私边界题尚未执行，因为当前系统没有标准化的评测`tool_state`注入接口。不能将这部分记为通过。

## 8. 修复优先级

### P0：转人工必须返回承接话术

至少包含：

- 已收到问题；
- 为什么需要人工；
- 客户需要补充什么；
- 等待期间能做什么；
- 不虚构处理完成状态。

### P0：提高模型链路稳定性

- 记录内部失败阶段；
- 为供应商502和JSON解析增加有限重试；
- 将请求和裁判逐题落盘；
- 支持续跑，不重复调用成功题。

### P1：建立动态业务事实接口

覆盖：

- 会员价格和有效期；
- 活动状态；
- 包赔规则；
- 商品价格和库存；
- 订单和付款；
- 课程开通和物流状态。

### P1：补强异议处理和方案调整

重点覆盖价格、不会养、不会开花、链接疑问、延迟发货和预算不足。

### P1：统一专业不确定性策略

在病害、图片和复花场景中明确：

- 什么信息足以判断；
- 什么情况必须追问；
- 什么情况提供临时措施；
- 什么情况转人工专家。

### P2：恢复多轮销售状态机

显式维护：

- 已知客户条件；
- 当前销售阶段；
- 未解决问题；
- 已推荐方案；
- 客户异议；
- 下一步动作。

## 9. 建议的下一轮验收门槛

完成P0修复后，先只运行30道单轮题：

| 指标 | 建议门槛 |
|---|---:|
| 系统请求成功率 | ≥98% |
| 空文本回复率 | ≤5% |
| 平均分 | ≥60 |
| 中位数 | ≥60 |
| 严重错误率 | ≤5% |

达到单轮门槛后再运行10道多轮题和15道边界题。
