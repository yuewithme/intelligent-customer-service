# 标签删除链路收口

## 任务目标

- 以管理后台中的实时标签目录为准，已删除的分类或标签不得被后端再次写入、使用或通过初始化恢复。
- 收口客户画像、系统标签、长期记忆与提示词上下文的删除同步。
- 保留投诉风险和人工接管等内部安全机制，但不将已删除分类继续作为可管理标签。

## 实施计划

1. 在标签目录元数据中持久化分类/标签删除标记，初始化和目录升级必须尊重删除标记。
2. 完善删除、重命名和重建同标识项时的标记维护。
3. 客户画像和运行状态写入前校验实时目录，并在整类删除时清理对应派生字段。
4. 长期记忆的提取、检索和上下文注入跳过已删除的痛点、产品兴趣等受管理事实。
5. 补充删除后不复活、新对话不重新写入以及内部安全机制保持有效的针对性测试。

## 完成结果

- 标签删除状态已使用 `tag_catalog_meta` 持久化；删除默认分类或标签后，重启和目录版本升级不会重新补入。
- 新版首次读取时会识别当前目录中已缺失的默认项，为线上已完成的删除补记删除标记。
- 删除整类标签时，对应客户画像派生字段会清空，相关长期记忆事实会终止生效。
- 画像分析、手工画像更新、记忆提取、校验、回填、投影、检索和提示词绑定均已改为校验实时标签目录。
- 内部风险与人工接管状态机制保留，不会因管理标签删除而失效。

## 验证情况

- 标签删除、默认值不复活、画像写入拦截、记忆事实停用等针对性测试：15 项通过。
- 客户画像和记忆相关最小回归：58 项通过，1 项排除。被排除用例因当前工作区并行开发的 SOP 节点校验改动而失败，与本次标签链路无关。
- 已执行修改文件的 Python 语法编译检查和差异格式检查。
- 本地未执行前后端构建；待提交后由 GitLab 流水线统一构建和部署一次。
