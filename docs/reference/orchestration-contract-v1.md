# 可插拔能力与经验包协议 v1

## 1. 目的

本协议定义智能客服从单一 Agent 演进为“业务数据基座 + 可插拔能力 + 经验包 + 可视化编排平台”时的第一版稳定边界。

本阶段只建立可校验的设计态契约和首单样板，不改变当前生产 Agent、工具执行器、SOP 路由或数据库结构。

机器可校验定义：

- `apps/api/app/domains/orchestration/schemas/definitions.py`
- `apps/api/app/domains/orchestration/data/capabilities/current_agent_capabilities.v1.json`
- `apps/api/app/domains/orchestration/data/experience_packages/orchid_first_order.v1.json`

## 2. 核心分层

```text
业务事实数据
客户 / 会话 / 标签 / 记忆 / 商品 / 订单 / 知识 / 素材
                         ↓
能力插件
系统实际能查询、写入、发送或通知什么
                         ↓
经验包
在什么场景进入、按什么步骤工作、允许使用哪些能力、如何结束
                         ↓
运行实例
某个客户固定使用哪个经验包版本、当前步骤和完整事件轨迹
```

必须保持以下边界：

- 能力插件不包含完整销售 SOP，只提供稳定、可审计的单项能力。
- 经验包不包含 Python 实现，只引用已经安装的能力版本。
- 商品、订单、素材和知识继续引用真实业务数据，不复制进经验包。
- 画布坐标只负责展示，不能参与运行判断。
- 已发布版本不可原地修改；运行实例固定引用一个经验包版本。

## 3. 能力插件

### 3.1 能力协议

`CapabilityManifest` 负责描述一个能力版本：

| 字段 | 作用 |
| --- | --- |
| `capability_id`、`version` | 稳定身份和版本引用 |
| `name`、`description`、`kind` | 业务名称、说明和能力类型 |
| `ui` | 管理端分组、图标、摘要和可见级别 |
| `business` | 业务动作、数据来源、AI 使用方式、客户触达、业务权限、执行结果和风险说明 |
| `input_schema` | 执行时允许接收的参数 |
| `output_schema` | 执行结果能够提供的数据 |
| `config_schema` | 租户或能力安装时可配置的字段 |
| `execution` | 后端执行器、超时、重试和幂等要求 |
| `permissions` | 能力需要的数据与操作权限 |
| `side_effects` | 客户状态、消息、外部写入或人工接管副作用 |
| `preconditions` | 运行前可强制检查的条件 |
| `usage_guidance` | 无法完全结构化的 Agent 使用边界 |
| `error_codes` | 经验包可以处理的稳定错误编码 |

第一版执行器只支持 `local_handler`：研发实现和发布代码，业务人员只能启停、配置和绑定能力，不能上传任意代码。

### 3.2 业务说明

每项能力必须提供完整的 `business` 说明，默认管理端只展示这些字段：

| 字段 | 回答的业务问题 |
| --- | --- |
| `action` | 这个能力具体会做什么 |
| `data_source` | 从哪个业务系统或资料库取得数据 |
| `ai_mode`、`ai_mode_description` | AI 能否主动使用，以及需要满足什么条件 |
| `customer_contact`、`customer_contact_description` | 调用后是否会直接联系客户，还是只辅助回复 |
| `staff_notification` | 是否会通知工作人员 |
| `permission_description` | 业务上允许读取或修改什么，明确禁止什么 |
| `result_description` | 执行成功后会得到什么业务结果 |
| `risk_level`、`risk_description` | 该能力的业务风险及必须防范的问题 |

`ai_mode` 和 `customer_contact` 必须分开表达。例如查询养护手册可以由 AI 主动调用，但查询本身不会把手册发给客户；发送素材是另一项会直接触达客户的能力。

能力标识、执行器、超时、重试、幂等、技术权限、错误码和输入输出协议属于研发信息，在管理端默认折叠。

### 3.3 管理端展示级别

| `visibility` | 展示方式 | 示例 |
| --- | --- | --- |
| `hidden` | 只在步骤运行时自动开放，不进入画布节点栏 | 读取客户上下文、记录长期记忆 |
| `configurable` | 业务人员可以在对话阶段中勾选 | 查询知识库、查询商品 |
| `draggable` | 可以成为可视化画布上的明确动作 | 发送商品卡片、发送素材、转人工 |

能力中心展示全部能力；经验包编辑器只展示当前用户有权限、当前租户已安装且与步骤类型兼容的能力。

### 3.4 硬条件与软指导

可由运行时事实判断的规则应放入 `preconditions`，例如商品卡片要求 `purchase_signal` 为 `interest` 或 `direct`。专业表达、语气和语义边界放入 `usage_guidance`。

硬条件失败时执行器必须拒绝调用；不能只靠提示词提醒 Agent。

## 4. 经验包

### 4.1 经验包协议

`ExperiencePackageDefinition` 是一份完整、可版本化的业务工作方式：

| 字段 | 作用 |
| --- | --- |
| `package_id`、`version` | 经验包身份和不可变版本 |
| `goals` | 经验包总体业务目标 |
| `entry` | 触发事件、进入条件、起始步骤和优先级 |
| `parameters_schema` | 安装经验包时由业务人员填写的参数 |
| `context_schema` | 运行步骤之间共享的结构化上下文 |
| `global_rules` | 所有步骤必须遵守的业务边界 |
| `capability_dependencies` | 所需能力及版本范围 |
| `steps` | 对话阶段、判断、动作和等待 |
| `transitions` | 带优先级和条件的步骤连线 |
| `outcomes` | 经验包的明确退出结果和后续经验包 |
| `success_metrics` | 运行看板需要衡量的业务结果 |
| `layout` | 可视化画布坐标，不参与执行 |

### 4.2 步骤类型

第一版只定义四种步骤：

| 类型 | 用途 |
| --- | --- |
| `agent_stage` | 一个有目标、有完成条件的连续对话阶段 |
| `decision` | 根据结构化事实和语义判断选择出口 |
| `action` | 明确调用一个可拖拽能力 |
| `wait` | 暂停运行实例，等待消息、业务事件或超时 |

开始由 `entry` 表达，结束由 `outcomes` 表达，不额外制造没有运行语义的开始、结束步骤。

### 4.3 对话阶段

`agent_stage` 是业务人员最常编辑的步骤，至少包含：

- `goal`：这一步最终要形成什么业务结果。
- `directions`：应该往哪些方向沟通，不能退化为固定话术。
- `collect`：需要沉淀到运行上下文的事实。
- `capabilities`：当前步骤允许或必须使用哪些能力。
- `completion`：什么情况下允许离开当前步骤。

普通客户回复不会产生“等待回复”节点。客户没有满足完成条件时，运行实例保持在当前对话阶段；只有跨时间暂停才使用 `wait`。

### 4.4 条件

条件分为两类：

- `fact`：订单、标签、时间、步骤输出等可由系统直接判断的事实。
- `semantic`：客户是否认可方案、当前价值是否已经说明清楚等需要模型理解的语义。

`fact` 条件必须提供路径、操作符和值；`semantic` 条件只允许提供明确的业务说明，运行时需要保存判断理由和证据。

同一步骤的转移按 `priority` 从小到大判断，最多只能有一条无条件默认转移。

## 5. 首单样板

`orchid.first_order` 将原兰花首单 SOP 压缩为三个业务阶段：

```text
需求诊断
  原破冰 + 挖需求 + 找痛点
       ↓
方案推荐
  原推品 + 塑品
       ↓
购买信号判断
  ├─ 有意向且有真实商品 → 发送商品卡片
  ├─ 明确拒绝 → 正常结束
  ├─ 需要人工 → 转人工
  └─ 其他 → 低压力试成交
       ↓
成交推进
  原试成交 + 逼单
       ↓
成交结果判断
  ├─ 已付款 → 售后养护经验包
  ├─ 明确拒绝 → 正常结束
  ├─ 需要人工 → 转人工
  └─ 其他 → 等待客户消息或付款事件
```

步骤合并只改变画布粒度，不删除原 SOP 的经验。原来的具体策略进入对应步骤的 `directions` 和全局规则。

## 6. 静态校验

`ExperiencePackageDefinition` 当前强制校验：

- 步骤、转移、结果和能力依赖 ID 唯一。
- 入口必须指向真实步骤。
- 所有连线必须指向真实步骤或结果。
- 步骤引用的能力必须声明为经验包依赖。
- 动作失败结果必须已经声明。
- 每个步骤至少有一个出口。
- 同一步骤最多一条默认出口。
- 所有步骤必须能够从入口到达。
- 画布布局不能引用不存在的步骤。

当前校验只证明定义结构完整，不代表生产运行引擎已经接入。

## 7. 后续数据映射

下一阶段建议使用以下持久化边界：

| 数据 | 建议存储 |
| --- | --- |
| 能力身份和当前状态 | `capability_definitions` |
| 不可变能力协议 | `capability_versions.manifest_json` |
| 租户启停和业务配置 | `capability_installations` |
| 经验包身份 | `experience_packages` |
| 不可变经验包定义 | `experience_package_versions.definition_json` |
| 经验包与租户、渠道、触发场景绑定 | `experience_package_bindings` |
| 当前客户运行位置和固定版本 | `workflow_instances` |
| 进入、停留、跳转、超时和人工事件 | `workflow_events` |
| 能力调用、耗时、错误和副作用 | `capability_executions` |

数据库保存完整版本快照；Pydantic 契约负责读写校验，管理端表单和画布共同编辑同一份定义。

## 8. 管理端现状与后续

截至 2026-08-26，管理后台已经提供只读“能力工作台”：

- 页面：`/operations/capability-workbench`
- API：`GET /api/v1/admin/orchestration/workbench`
- 数据来源：经过本协议校验的静态能力目录和经验包定义
- 展示内容：能力统计、业务能力卡片、业务动作、数据来源、AI 使用方式、客户触达、业务权限、执行结果、引用位置，以及经验包步骤、连线、结果和步骤详情

当前页面不写入数据库，不允许修改、拖拽或发布经验包，也不参与生产 Agent 运行。它用于先验证业务展示方式；后续数据源从静态文件切换为数据库时，管理端聚合 API 可以保持稳定。

后续编辑形态仍以经验包中心为默认入口，不从空白画布开始：

默认入口是经验包中心，不是空白画布：

1. 从模板、复制、SOP 文档或自然语言创建草稿。
2. 先展示入口、三个到五个业务阶段和结果的流程概览。
3. 点击阶段后，在右侧填写目标、方向、采集数据、允许能力和完成条件。
4. 校验能力依赖、缺失出口、危险副作用和未配置参数。
5. 使用测试客户上下文进行模拟。
6. 发布不可变版本，再绑定租户、渠道和触发条件。

空白画布和复杂连线放入高级编辑模式。普通业务人员主要复制经验包并调整业务参数与步骤说明。
