# Sales Agent Harness V2 架构调整计划

## 目标

把当前以意图、阶段、路由和固定话术为主的回复链路，逐步调整为一个具备自主判断能力的
Sales Agent：它围绕长期信任和成交目标理解客户、选择经验、调用工具、组织回复并根据结果继续判断；
系统只控制真实数据、权限、执行安全和微信通道稳定性。

本计划不要求推翻现有架构。迁移采用影子验证和逐步替换，任何旧链路只有在新 Agent 通过评测后才退出主决策。

## 目标结构

```text
客户消息
  -> 微信入站队列、去重、合并、输入规范化
  -> 客户工作区（对话、事实、关系、承诺、待办）
  -> 单一 Sales Agent 循环
       -> 销售核心（始终加载）
       -> 简短能力目录（始终可见）
       -> 按需加载工具、经验和参考资料
       -> 自主生成回复或工具动作
  -> 工具执行与硬边界校验
  -> 逻辑回复包
  -> 原有微信出站队列
  -> 真实发送结果回写客户工作区
```

## 当前能力怎么处理

| 当前能力 | 处理方式 | 说明 |
| --- | --- | --- |
| 易云回调、入站合并和消息去重 | 保留 | 属于通信基础设施 |
| 微信出站队列、限速、顺序、重试 | 保留 | Agent 不直接控制底层发送节奏 |
| 会话记录和长期记忆 | 保留并改造 | 组装成 Agent 可理解的客户工作区 |
| 商品、有赞、订单、养护资料能力 | 保留并工具化 | 由 Agent 自主选择调用 |
| 人工接管、日志和评测设施 | 保留 | 作为可靠性和运营闭环 |
| Persona 的 SOUL、POLICY、STYLE | 重组 | 拆为销售核心、硬边界和表达风格 |
| 意图识别、销售阶段、标签 | 降为观察器 | 用于分析和评测，不再做主路由门禁 |
| ReplyPlan、策略优先级、固定路由 | 逐步退出主决策 | 影子期保留用于对照和回滚 |
| 固定话术、阶段模板、关键词触发 | 降为经验或案例 | 不再直接决定客户回复 |
| 固定未购买 SOP | 改造成唤醒能力和经验 | 唤醒时重新判断，不预写死回复 |

## 实施阶段

### 阶段 1：业务输入和基线冻结

- 完成本目录全部填写文档。
- 盘点现有工具、资料、数据源和发送能力。
- 固化一组真实对话回归集和当前系统基线。
- 将现有规则逐条分类为硬边界、业务事实、柔性经验、观察指标或待删除补丁。

成功检查：每条现有关键规则都有归属；没有把尚未理解的规则直接删除。

### 阶段 2：建立最小 Harness

- 建立精简的 Sales Core。
- 建立客户工作区契约。
- 建立工具双层描述：短描述始终可见，完整说明按需加载。
- 建立销售经验包和按需加载入口。
- 建立统一的逻辑回复包，支持文字、商品卡片、资料卡片和后续承接话术。

成功检查：Agent 不依赖固定意图路由，也能完成普通咨询、选品、资料、订单和拒绝场景。

### 阶段 3：接入只读工具并影子运行

- 先开放商品、资料、订单、客户记忆等只读工具。
- 新 Agent 影子生成决策，不发送给客户。
- 对比当前生产回复、销售人员判断和新 Agent 判断。
- 优先通过工具注释、经验和上下文改进，不为单个案例增加流程补丁。

成功检查：工具选择准确；没有编造业务事实；正常表达不再被关键词或固定意图漏掉。

### 阶段 4：接入真实动作

- 开放资料卡片、商品卡片、人工接管和唤醒任务等动作。
- 写操作只接受真实工具返回的引用，不接受模型自行生成链接、价格或资源 ID。
- Agent 输出逻辑回复包，继续经过现有微信出站队列。
- 明确 queued、sent、failed、cancelled，只有 sent 才写入“已发送”记忆。

成功检查：卡片和文本顺序正确；失败不会被描述成成功；重复执行可被拦截。

### 阶段 5：灰度接管主决策

- 从低风险会话开始灰度。
- 意图、阶段和旧策略保持影子观察，不控制新 Agent。
- 持续检查成交推进、客户体验、工具精度、幻觉和人工接管质量。
- 达到验收标准后，再逐步移除重复的旧路由和话术补丁。

成功检查：质量不低于基线，严重错误为零，微信发送稳定性不退化，并可随时回滚。

## 明确不做

- 不一次性删除所有旧链路。
- 不把每个销售阶段重新包装成一个硬编码 Skill。
- 不让模型直接控制微信限速、重试和底层发送。
- 不把所有销售资料一次性塞进系统提示词。
- 不因单个坏案例立即增加关键词规则。
- 第一版不引入多个销售子 Agent；先把一个主 Agent 的上下文、工具和反馈闭环做好。

## 预填写的架构决定

1. 【建议草案】同意“先影子、再只读工具、再真实动作、最后灰度替换”的顺序。

   理由：这是释放 Agent 主动性同时保留生产回滚能力的最小风险路径。影子期重点观察 Agent 的判断和工具选择，不用旧路由结果纠正新 Agent。

2. 【建议草案】意图、销售阶段和标签先保留为观察指标，但不再拥有最终路由权。

   理由：它们仍可用于分析、运营看板和新旧对比，但不应阻止主 Agent 识别其他表达或调用合适工具。

3. 【建议草案】第一版只使用一个主 Sales Agent，不设计多 Agent 分工。

   理由：当前最需要解决的是主 Agent 的目标、上下文、工具和反馈闭环，多 Agent 会增加交接损耗和调试复杂度。

4. 【建议草案】新架构优先改善的三个真实问题：

   - 客户使用非标准、间接或组合表达时，现有关键词和意图路由容易漏识别或走错链路。
   - 回复和资料发送受固定阶段、轮数、话术与节点约束，不能结合客户关系自然推进成交。
   - 模型不能自主发现和组合商品、资料、订单、记忆与唤醒能力，导致智能被外部流程替代。

5. 【建议草案】绝不能退化的现有能力：

   - 微信消息队列和通道稳定性。
   - 商品、价格、库存、订单、物流和资料引用的事实真实性。
   - 人工接管、客户退订、发送状态、长期记忆和生产回滚能力。

## 【请修改】你只需要重点审阅

- 是否同意旧意图、阶段和路由在灰度期只做观察，不干预主 Agent。
- 是否有必须提前进入第一阶段的写操作。
- 是否有上述“绝不能退化”之外的生产底线。
