# Sales Agent Harness V2 架构调整计划

## 实施结果

本计划已完成并部署生产。主聊天入口现在只运行一个自主 Sales Agent 循环；意图分类、销售阶段、ReplyPlan、固定资料话术、固定 SOP 和影子评测不再拥有运行时决策权。商品、资料、订单、记忆、唤醒与人工接管均由 Agent 按上下文选择工具，微信收发仍经过原有风控队列。

替换前代码已建立并推送 Git 基线标签 `pre-agent-harness-v2`。旧业务数据库表没有执行破坏性删除，避免损害数据恢复；运行时回退依赖 Git 标签或对本次提交执行 `git revert`，不保留双轨开关。

## 目标

把当前以意图、阶段、路由和固定话术为主的回复链路，直接替换为一个具备自主判断能力的
Sales Agent：它围绕长期信任和成交目标理解客户、选择经验、调用工具、组织回复并根据结果继续判断；
系统只控制真实数据、权限、执行安全和微信通道稳定性。

项目采用直接替换，不运行影子流量、灰度流量或新旧双轨。新 Agent 已通过本地回归并接管生产主决策入口；
旧决策实现不作为运行时备用链路，依靠 Git 基线、清晰提交和可逆部署保留回退能力。

## 目标结构

```text
客户消息
  -> 微信入站队列、去重、合并、输入规范化
  -> 客户工作区（对话、事实、关系、承诺、待办）
  -> 单一 Sales Agent 循环
       -> 销售核心（始终加载）
       -> 简短能力目录（始终可见）
       -> 按需加载工具、经验和参考资料
       -> 自主生成回复或工具动作
  -> 工具执行与硬边界校验
  -> 逻辑回复包
  -> 原有微信出站队列
  -> 真实发送结果回写客户工作区
```

## 当前能力怎么处理

| 当前能力 | 处理方式 | 说明 |
| --- | --- | --- |
| 易云回调、入站合并和消息去重 | 保留 | 属于通信基础设施 |
| 微信出站队列、限速、顺序、重试 | 保留 | Agent 不直接控制底层发送节奏 |
| 会话记录和长期记忆 | 保留并改造 | 组装成 Agent 可理解的客户工作区 |
| 商品、有赞、订单、养护资料能力 | 保留并工具化 | 由 Agent 自主选择调用 |
| 人工接管、日志和评测设施 | 保留 | 作为可靠性和运营闭环 |
| Persona 的 SOUL、POLICY、STYLE | 重组 | 拆为销售核心、硬边界和表达风格 |
| 意图识别、销售阶段、标签 | 退出运行时决策 | 如后续确有分析价值，可由离线评测重新计算，不注入主 Agent 路由 |
| ReplyPlan、策略优先级、固定路由 | 退出主决策 | 不保留新旧双轨，旧实现仅存在于 Git 历史 |
| 固定话术、阶段模板、关键词触发 | 降为经验或案例 | 不再直接决定客户回复 |
| 固定未购买 SOP | 删除 | 不再保留自动唤醒或预写跟进话术 |

## 已完成的实施顺序

### 步骤 1：冻结文档和 Git 基线

- 以本目录最终文档作为实现依据。
- 盘点现有工具、资料、数据源和发送能力。
- 固化一组真实对话回归集和当前系统基线。
- 将现有规则逐条分类为硬边界、业务事实、柔性经验、观察指标或待删除补丁。
- 在改造前提交当前可运行代码并建立明确 Git 基线标记；后续按职责拆分提交，回退使用 `git revert` 和重新部署，不依赖破坏性历史重写。

成功检查：每条现有关键规则都有归属；没有把尚未理解的规则直接删除。

### 步骤 2：建立最小 Harness

- 建立精简的 Sales Core。
- 建立客户工作区契约。
- 建立工具双层描述：短描述始终可见，完整说明按需加载。
- 建立销售经验包和按需加载入口。
- 建立统一的逻辑回复包，支持文字、商品卡片、资料卡片和后续承接话术。
- 建立“服务中”客户独立的三时段素材触达，不让 Agent 自主创建自动唤醒。

成功检查：Agent 不依赖固定意图路由，也能完成普通咨询、选品、资料、订单和拒绝场景。

### 步骤 3：统一工具与执行边界

- 接入商品、资料、订单、客户记忆等查询工具，以及卡片、记忆和人工接管动作。
- 写操作只接受真实工具返回的引用，不接受模型自行生成链接、价格或资源 ID。
- Agent 输出逻辑回复包，继续经过现有微信出站队列。
- 明确 `queued`、`sent`、`failed`、`cancelled`，只有服务中触达整包全部 `sent` 才完成任务。
- 优先通过工具注释、经验和上下文改进，不为单个案例增加流程补丁。

成功检查：工具选择准确；没有编造业务事实；卡片与文本顺序正确；失败不会被描述成成功；正常表达不再被关键词或固定意图漏掉。

### 步骤 4：离线回归并直接替换

- 使用现有 55 条 dataset v2、10 个核心案例和 77 个清洗会话进行离线回归。
- 覆盖非标准表达、商品、资料、订单、服务中触达、拒绝、人工接管、工具失败和发送状态。
- 本地验证通过后，将主决策入口一次性切换到新 Sales Agent，不运行旧链路对照，不按客户比例灰度。
- 部署后监控事实错误、工具失败、队列送达、重复触达和人工接管；出现阻断级问题时回退对应 Git 提交并重新部署。

成功检查：新入口独立完成主决策；旧路由不再被调用；微信发送稳定性不退化；Git 回退路径已演练且不需要保留运行时双轨。

## 明确不做

- 不保留旧决策链作为运行时备用路径；需要恢复时使用 Git 回退。
- 不把每个销售阶段重新包装成一个硬编码 Skill。
- 不让模型直接控制微信限速、重试和底层发送。
- 不把所有销售资料一次性塞进系统提示词。
- 不因单个坏案例立即增加关键词规则。
- 第一版不引入多个销售子 Agent；先把一个主 Agent 的上下文、工具和反馈闭环做好。
- 不把“每日必须触达”误写成固定发送话术；系统规定是否必须完成，Agent 决定如何完成。

## 最终架构决定

1. 新架构通过离线回归后直接替换旧主决策链，不做影子运行、流量灰度或双轨对照。

   回退依靠 Git 基线和可逆提交，不为回退继续维护一套运行时旧架构。

2. 意图、销售阶段和标签不再拥有运行时路由权，也不作为 Agent 调用工具或回复客户的前置条件。

   如运营分析确实需要，可以离线生成观察指标，但不反向控制 Agent。

3. 第一版只使用一个主 Sales Agent，不设计多 Agent 分工。

   理由：当前最需要解决的是主 Agent 的目标、上下文、工具和反馈闭环；多 Agent 会增加交接损耗和调试复杂度，暂不设计多 Agent。

4. 新架构优先改善的三个真实问题：

   - 客户使用非标准、间接或组合表达时，现有关键词和意图路由容易漏识别或走错链路。
   - 回复和资料发送受固定阶段、轮数、话术与节点约束，不能结合客户关系自然推进成交。
   - 模型不能自主发现和组合商品、资料、订单、记忆与唤醒能力，导致智能被外部流程替代。

5. 绝不能退化的现有能力：

   - 微信消息队列和通道稳定性。
   - 商品、价格、库存、订单、物流和资料引用的事实真实性。
   - 人工接管、通道不可发送状态、发送状态、长期记忆和 Git 回滚能力。

6. 自动触达只保留“服务中”客户的固定三时段审核素材任务，不由 Agent 自主创建或生成。
