```text

  -> 单一 Agent 循环（默认 sop_scope=service）
```

当前 SOP 作用域：

- `service`：生产默认。先解决问题、履行服务、维护关系，相关时介绍会员权益；仅在客户出现真实选购需求时探索复购。
- `first_order`：封存备用。保留原新客挖需、陪伴服务优先、痛点转服务、塑品和试成交经验，不在生产默认流程加载。
- `shared`：事实核验、知识、订单、资料、权限、记忆、人工接管和消息发送等共同能力。

## Agent 自主权与系统硬边界

Agent 自主决定每轮商业判断、关系目的、表达方式、工具组合、资料时机和商品卡片时机。系统只硬控以下内容：

- 商品、价格、库存、订单、物流、权益、资料引用和优惠结果必须来自真实工具。
- `prepared`、`queued` 不得表述为 `sent`；未被 Agent 放入最终回复包的预备卡片不会发送。
- 退款、赔偿、改价、改订单、客户要求人工等授权动作必须转人工。
- 客户隔离、真实引用、参数校验、近期重复资料、防内部状态泄露和未核实促销话术。
- 原首单开场硬校验只在 `sop_scope=first_order` 时生效；服务型新好友入口不执行该校验。
- 微信队列顺序、依赖、限速、重试、状态回写和技术不可发送状态。

问题数量、编号、项目符号、Markdown 和普通引号属于质量提示，不再阻止安全回复发送。运行时只允许未核实事实、权限、真实引用、发送状态、内部泄露和固定开场缺失等硬违规触发一次定向重写；修复失败时转人工，不再用通用销售兜底覆盖模型原回复。

普通表情、短句、“嗯”“好的”等不按垃圾信息丢弃，会交给 Agent 结合上下文理解；只过滤明确的传输占位、系统事件和无法形成客户语义的 UI 噪声。

默认服务思路是“问题解决 → 必要追问 → 权益与品牌承接 → 长期关系 → 有信号时复购”。养护咨询必须先给出有依据、可执行的回答，再只了解一个会改变判断或后续陪伴的客户事实。会员权益只选择与本轮问题最相关的一项，并先通过工具核实；普通养护痛点不构成购买需求，不触发商品卡片。客户明确想添花、选品种或了解价格入口后，才进入复购查询和卡片流程。

已购客户的问题得到解决，客户用“好的、谢谢、明白了、知道了”等认可并自然收口时，Service SOP 会按需加载经验，强烈建议在这次收口中完整覆盖“持续咨询心智 → 会员吸引点 → 未来鉴赏偏好挖需”，通常按语义拆成两到三条短消息。它属于 Agent 学习和迁移的销售经验，不由运行时代码按关键词、固定句式或消息数量强制。每周上新多款铭品供鉴赏、会员专属折扣活动、后续主动分享实拍与优惠是业务确认可直接表达的长期钩子；客户追问具体日期、品种、数量、折扣、金额、条件或有效期时不编造，简短说明每期安排不同后转向鉴赏偏好。鉴赏偏好会作为有原话证据的稳定记忆保存，本身不构成购买信号，不触发商品查询或卡片。

新好友开场直接发送业务方确认的老客服务话术，不再调用模型改写，不插入原首单品牌图片，也不强制询问盆数和品种。开场后的自然对话仍可根据实际问题逐步了解盆数、品种、地区、环境、经验和偏好。

## Git 回退

优先使用可逆提交：

1. 找到本次 Harness V2 提交。
2. 在 `main` 上执行 `git revert <提交号>` 并正常推送。
3. 重新部署回退后的 `main`。

若需要完整恢复替换前版本，可从标签 `pre-agent-harness-v2` 构建部署。不要 force-push，不要对生产工作树执行 `reset --hard`。回退代码不会自动删除新 Agent 创建的表；这些新增表对旧版本无调用影响。
