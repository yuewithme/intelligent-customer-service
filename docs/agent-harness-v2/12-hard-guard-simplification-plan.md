# 12 硬规则精简与自主销售推进改造计划

> 实施状态：已于 2026-08-06 完成。当前主链已按本方案直接替换，没有保留表达规则阻断双轨。

## 一、改造结论

本轮不删除全部校验，而是把系统职责收缩为三件事：事实真实、权限安全、执行可靠。
销售表达、追问数量、话题切换、资料释放时机、推服务还是推商品等依赖语境的判断，交还给主 Agent。

一句话原则：**系统只阻止不能发生的事情，不否决只是表达得不够理想的回复。**

本计划直接修改当前主链路，不建立影子链、灰度链或旧规则兼容层。开发和验证在本地完成，
通过 Git 提交保留回退能力，随后由云端拉取 `main` 部署。

## 二、这次要解决的问题

当前运行时把部分销售经验实现成了正则和固定门禁。例如“每轮最多问一个有价值的信息点”被实现为疑问词计数，
一个自然问题里同时出现“有没有”和“还是”也可能被判断为多个问题。模型回复随后连续重写，消耗完五轮执行预算，
最终被一条与当前问题无关的固定兜底替换。

这会造成四个直接问题：

1. 没有事实风险的 Agent 回复被表达规则误杀，固定兜底反而更差。
2. Agent 为通过校验不断改句子，把注意力从客户和成交转向格式合规。
3. 重试反复携带完整客户工作区和旧输出，Prompt 持续膨胀，成本和延迟增加。
4. Harness 反复强调“继续挖需”和“每轮一个问题”，容易让 Agent 把追问当成默认动作，围绕一个症状一直深挖，错过价值塑造、推服务和推品时机。

## 三、规则重新分类

### 3.1 继续作为硬边界

这些规则无论语境如何都不能突破，继续由服务端确定性校验：

| 类别 | 保留内容 | 系统处理 |
| --- | --- | --- |
| 动态事实 | 商品、价格、库存、订单、物流、活动、优惠、资料权益和发送状态必须来自真实工具结果 | 无来源时阻止相关断言，允许重写一次；需要授权时转人工 |
| 工具引用 | 商品、资料、订单和卡片只能使用工具返回的真实引用；`queued/prepared` 不能说成 `sent` | 拒绝未知引用和虚假成功状态 |
| 权限与身份 | 客户隔离、租户隔离、订单归属、隐私、退款、改价、地址修改等授权边界 | 服务端强制校验，越权动作转人工 |
| 通道安全 | 微信排队、限速、顺序、幂等、重试、拉黑、退订、`forbidden` 和人工接管状态 | Agent 不能绕过队列或不可发送状态 |
| 事实承诺 | 不编造销量、疗效、养活承诺、虚假稀缺、最低价、名额和人工处理结果 | 删除未核实断言或转人工 |
| 输出契约 | Agent 输出必须是可解析的结构化决策；准备发送的引用必须存在 | 独立进行有限的契约修复，不与工具轮数共用预算 |
| 固定业务事件 | 新好友开场必须完成自我介绍、开场图片、盆数与主要品种挖需 | 只固定语义动作和消息顺序，不固定具体话术 |

### 3.2 从硬拦截降为质量提示

以下项目可以保留在 Prompt、测试和运营质量指标中，但不能再触发整轮回复作废：

| 当前规则 | 新形态 |
| --- | --- |
| `too_many_customer_questions` | 记录“本轮问题可能过多”，不阻止发送；重点判断是否在收集同一个有价值的信息，而不是统计疑问词 |
| `unnecessary_customer_quotes` | 作为微信口语风格建议，不因出现任意引号拒绝回复 |
| `non_conversational_list_style` | 作为表达质量提示；只有泄露内部结构或无法面向客户阅读时才按真正硬边界处理 |
| 每轮必须继续追问 | 删除“必须”；问题只是可选动作，很多轮可以不提问 |
| 必须完整诊断症状后才能推进 | 删除；以商业匹配所需信息是否足够为准，不追求在聊天中完成专业会诊 |
| 固定阶段、固定轮数、固定字段才能推服务、推品或发资料 | 继续作为经验，不作为代码门禁 |
| 软拒绝后的固定回复方式 | 只保留降低压力、继续经营关系的原则，由 Agent 自主组织本轮动作 |

### 3.3 直接删除的补丁

- 删除“表达质量不合格就连续重写，直到耗尽 Agent 总步数”的运行时路径。
- 删除因问题数量、引号或列表表达触发的固定通用兜底。
- 删除工具执行、结构修复和表达重写共用同一个五轮预算的设计。
- 删除对疑问词数量的语义替代；不再用“有没有、还是、怎么”等词出现几次推断客户被问了几个信息点。
- 删除正常销售回复中的万能承接句，不允许它覆盖已有的安全 Agent 原回复。

## 四、Agent 的新销售判断方式

### 4.1 先处理客户当前问题

每轮先识别客户此刻真正要解决的事情，并给出有用承接。客户问养护问题时先回答可安全回答的部分；
客户问商品、价格、库存、购买方式或订单时，直接使用对应工具，不得为了走挖需流程而回避当前问题。

### 4.2 用“商业充分性”结束挖需

Agent 不追求把所有信息问全，只判断现有事实是否足以回答三个问题：

- 客户主要想解决什么；
- 哪些已知条件决定了更适合服务还是商品；
- 为什么下一步建议对这个客户有价值。

盆数、养兰时间、反复失败和具体痛点都是判断证据，不是必填字段。已经知道盆数和痛点，或已经知道客户经验较短且反复养不好时，
通常足以开始解释原因、塑造团队价值并判断服务方向。只有某个未知会明显改变下一步商业动作时，才继续问。

### 4.3 问题不是默认结尾

每轮由 Agent 自主选择最有价值的主要动作，例如：

- 回答客户正在问的问题；
- 补一个真正会改变推荐的信息；
- 说明萧岚苑与普通卖货商家的差异；
- 介绍陪伴养兰服务；
- 查询并推荐合适商品；
- 处理顾虑或推进下单；
- 发送匹配资料并自然承接下一步；
- 暂时不提问，用一次真实帮助建立信任。

这些是可选思路，不新增固定状态机或动作枚举。商业判断中应说明为什么本轮选择当前动作，
但客户可见回复不展示内部判断。

### 4.4 及时从症状细节转向服务或商品

如果继续追问叶尖、叶基、软硬、速度等细节不会改变“客户需要基础养护体系和持续指导”的判断，Agent 应停止深挖，
先给初步处理建议，再自然了解过去是否有人持续指导，随后说明萧岚苑通过单品知识和结合实际情况的实时指导如何帮助客户。

如果客户已经明确想买、问价格、问品种、要链接，或已知事实足以支持可靠匹配，Agent 应进入真实商品查询和推荐；
不能因为还有养护细节未知就一直停留在诊断阶段。

## 五、运行时改造

### 5.1 校验结果分层

将当前单一 `violations` 拆成：

- `hard_violations`：事实、权限、引用、发送状态和真正不可突破的安全问题；
- `quality_flags`：问题数量、引号、列表感、客服腔和其他表达建议。

只有 `hard_violations` 可以阻止发送。`quality_flags` 进入日志和评测，不改变本轮发送结果。

### 5.2 分离执行预算

- 工具循环只计算真实模型决策和工具调用步骤。
- JSON 契约修复使用独立的小预算，不重复执行已经成功的工具。
- 硬边界重写最多执行一次，并只发送简短的违规事实和可用工具结果，不重复注入完整客户工作区。
- 表达质量不触发在线重写。

### 5.3 新的失败处理顺序

1. 有安全的 Agent 最终回复：直接发送，即使存在质量提示也不替换。
2. 只有部分动态事实未核实：要求 Agent 删除或改写未核实部分一次，保留其他有用内容。
3. 涉及必须授权的动作：转人工，不生成假处理结果。
4. 模型超时或持续无法输出合法结构：进入系统重试；仍失败则创建人工承接，不发送与上下文无关的销售兜底。
5. 固定开场等明确业务事件可以有专用安全结果，但不得复用为普通会话兜底。

### 5.4 控制 Prompt 膨胀

- 客户工作区和本轮客户消息只注入一次。
- 后续工具步骤只追加新增工具结果，不重复整份工作区。
- 校验修复只携带上一条待修复回复、具体硬违规和已核实事实。
- 不把历次被拒回复、历次完整工具结果和重复客户消息无限累积到同一轮上下文。

## 六、可观测性与复盘

以后必须能够回答“模型原来生成了什么、为什么被拦、最终发了什么”。每次 Agent 尝试记录：

- `trace_id`、尝试序号、模型、Provider Request ID 和耗时；
- 经脱敏和长度限制后的原始结构化决策，至少保留客户可见 `final_response`；
- `hard_violations`、`quality_flags` 和最终处理结果；
- 是否发生工具调用、重写、人工接管或真正故障兜底；
- 最终发送的消息与原回复之间的差异。

日志只供有权限的管理端诊断，执行客户隐私脱敏和有限保留周期，不出现在客户回复中。

## 七、实施步骤与成功检查

### 步骤 1：全量盘点现有硬规则

- 盘点 Agent Runtime、Prompt、工具执行、资料/商品发送、人工接管和微信队列中的所有确定性判断。
- 每条规则归入：硬边界、基础设施、柔性经验、质量提示或删除补丁。
- 对无法说明“无论语境如何都不能突破”的规则，默认不保留为硬门禁。

成功检查：所有在线阻断点都有明确业务理由，不再存在仅为话术好看而拒绝整轮回复的代码。

### 步骤 2：重构校验与重试循环

- 拆分 `hard_violations` 和 `quality_flags`。
- 删除表达类硬拦截和固定通用兜底路径。
- 分离工具、契约修复和硬边界重写预算。
- 避免重试上下文重复膨胀。

成功检查：单个自然复合问题、正常引号或口语列表不会触发兜底；未核实价格、库存和发送成功仍被可靠阻止。

### 步骤 3：精简 Sales Core 与经验

- 合并重复出现的“每轮一个问题”和“继续挖需”要求。
- 明确“最多一个问题”不是“每轮必须提问”。
- 加入商业充分性、先回答当前问题、及时转入价值塑造/服务/商品的原则。
- 保留盆数、痛点、经验、失败史和原商家指导等优质经验，但不转成字段门禁。

成功检查：Agent 能根据同一批客户事实选择继续了解、推服务或推品，而不是固定追问下一个症状细节。

### 步骤 4：补齐诊断日志

- 保存每次模型尝试的可复盘输出和处理结果。
- 管理端按 `trace_id` 展示原回复、拦截原因和最终回复。
- 对内容执行脱敏、权限控制和保留周期管理。

成功检查：再出现兜底时，可以直接调出每次模型回复，而不是只能看到一个违规名称。

### 步骤 5：针对性回归

至少覆盖：

- “老叶发黄怎么处理”场景：先回答，再转向服务价值或商业下一步，不连续追问细枝末节；
- 一个自然问题同时包含“有没有”和“还是”：允许发送；
- 回复出现普通引号或自然分段：允许发送；
- 已知盆数和痛点：停止横向盘问并判断服务方向；
- 明确购买、价格或链接信号：及时查询商品并推进；
- 未核实价格、库存、订单、优惠和资料发送状态：继续硬拦；
- 工具失败和模型超时：不编造，不用万能废话覆盖上下文；
- 新好友开场：保持自我介绍、图片、盆数和主要品种问题的固定语义结构；
- 资料发送后：继续挖需或转入推品，不被动结束；
- 软拒绝和礼貌回复：降低压力但保持商业目的。

成功检查：正常回复不再因表达规则进入 `sales_agent_fallback`；硬事实错误拦截能力不退化；Agent 能自然改变销售动作。

### 步骤 6：直接替换与 Git 回退

- 本地完成最小相关测试和完整 Agent 主链回归。
- 检查差异、敏感信息和配置一致性后提交并推送 `main`。
- 云端只拉取已提交代码并重建服务，不直接修改服务器源文件。
- 出现阻断级事实或通道问题时，使用 Git 提交回退并重新部署。

成功检查：生产只运行精简后的单一主链；不存在新旧校验双轨；回退不依赖保留旧运行时架构。

## 八、明确不做

- 不把“回答、挖需、价值、推服务、推品、成交”重新编码成固定阶段机。
- 不为每个坏案例增加关键词、正则或专用回复模板。
- 不让第二个评审 LLM 在线决定主 Agent 的普通回复能否发送。
- 不因追求微信口语风格削弱价格、库存、订单、权限和发送状态的真实性校验。
- 不把全部销售经验永久塞入系统 Prompt；继续使用精简核心和渐进式披露。
- 不再用固定万能话术掩盖正常 Agent 回复或运行时设计问题。

## 九、实施结果

- 运行时已经拆分 `hard_violations` 与 `quality_flags`；只有前者可以阻止发送。
- “多问题、列表感、普通引号”只写入诊断日志，不再触发模型重写或固定兜底。
- 工具轮次、JSON 契约修复和硬边界重写使用独立预算；硬违规最多定向重写一次。
- 客户消息与完整工作区只注入一次，后续仅追加新工具结果，避免同轮 Prompt 重复膨胀。
- 普通会话持续失败时转人工；只有新好友开场保留专用安全结果，不再发送万能承接句。
- 每次尝试会记录受限长度的结构化决策、Provider Request ID、硬违规、质量提示和处理结果；管理端会话详情可通过同一 `trace_id` 联合查看模型调用日志。
- Sales Core 与渐进披露经验已强调商业充分性、先处理当前问题、问题非默认动作，以及及时从症状细节转入团队价值、服务或商品。
- 本地后端完整回归为 458 项通过、0 项失败。
