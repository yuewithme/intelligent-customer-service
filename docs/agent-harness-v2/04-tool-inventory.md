# 04 工具清单与渐进式披露

工具负责提供真实能力，不负责规定销售流程。Agent 自主决定是否调用；系统负责参数、权限、幂等和执行状态。

## 双层工具描述规范

每个工具有两层说明：

1. `short_description`：始终可见，一到两句话，说明“什么时候用”和最重要的边界。
2. `full_instructions`：Agent 选择相关能力后才加载，包含完整参数、结果、失败和副作用。

短描述示例：

```text
product.search
当客户需求可能对应可售商品时查询真实商品、价格和适用场景。普通养护问题且不涉及选品时不要调用。
```

## 预填写的工具目录

| 工具 | `short_description` | 类型 | 当前基础 | 披露方式 |
| --- | --- | --- | --- | --- |
| `capability.search` | 不确定有哪些工具或经验能帮助当前任务时，搜索最相关能力。已经知道具体工具时不要调用。 | 只读 | 需要新增 | 始终可见 |
| `customer.get_context` | 当前判断需要客户历史、偏好、购买、承诺或待办时读取证据化客户工作区。不要用它猜测动态价格和订单状态。 | 只读 | Memory 2.0 已有基础 | 每轮自动注入摘要，完整 Schema 按需 |
| `product.search` | 客户需求可能对应可售商品或服务时，查询真实商品、价格、库存和适配字段。纯养护咨询且无购买关系时不要调用。 | 只读 | 商品目录与有赞能力已有 | 完整 Schema 延迟加载 |
| `product.get` | 已有明确 `product_ref`，需要核实完整规格、权益或卡片信息时读取详情。不要用模糊名称调用。 | 只读 | 有赞 `get_product` 已有 | 由 `product.search` 结果引导加载 |
| `product.send_card` | 客户适合查看或购买已确认商品时，发送真实 `product_ref` 对应卡片。不得自行拼接链接或发送未核实商品。 | 写入 | 微信小程序卡片和队列已有 | 选择商品后才加载 |
| `care_manual.search` | 需要为具体品种、商品或养护主题查找已发布养护手册时使用。通用常识可直接回答时不必调用。 | 只读 | 养护手册库已有 | 相关养护 Skill 中披露 |
| `material.search` | 资料可能帮助当前问题、建立价值或形成后续触点时，搜索匹配资料及使用条件。不要把搜索等同于发送。 | 只读 | 陪伴资料与手册库部分已有 | 相关时加载 |
| `material.send` | 决定此刻释放资料有助于客户和成交时，发送真实 `material_ref`。不得绕过权益、重复发送和微信队列。 | 写入 | 资料卡片、图片和队列已有 | 搜索返回引用后加载 |
| `order.search` | 客户询问订单、付款、发货或物流时，按当前客户身份和客户主动提供的手机号查近期订单。不得按模糊姓名跨客户查询。 | 只读 | 有赞订单查询已有 | 订单场景加载 |
| `order.get` | 已有明确 `order_ref`，需要核实某笔订单详情时使用。不得用于修改、退款或取消。 | 只读 | 有赞单笔订单已有 | 由 `order.search` 引导加载 |
| `memory.record` | 当前对话产生了稳定客户事实、明确偏好、承诺、纠正或待办时，提交带证据的记忆候选。不要记录短暂寒暄和模型猜测。 | 写入候选 | Memory 2.0 已有候选、验证和合并 | 相关时加载 |
| `wakeup.schedule` | 未来某个时间值得重新读取上下文并判断是否联系时创建唤醒。不要提前写死未来回复，也不要绕过退订。 | 写入 | 现有 SOP / 定时能力可改造 | 跟进经验中披露 |
| `human.handoff` | 客户要求人工、需要授权写操作、重大售后或现有证据不足以安全处理时转人工，并携带摘要和未完成事项。 | 写入 | 人工接管与通知已有 | 始终可发现，完整 Schema 按需 |

## 完整工具说明草案

| 工具 | 使用前提 | 关键输入 | 关键输出 | 不使用 / 失败边界 |
| --- | --- | --- | --- | --- |
| `customer.get_context` | 已解析当前租户和客户身份 | `subject_ref`、当前任务摘要 | 当前事实、相关经历、工作状态、未知和证据 | 不返回无关隐私；检索失败时使用当前对话，不假装记得 |
| `product.search` | 有商品、服务、预算或选品关系 | 查询词、客户关键条件、数量上限 | `product_ref`、名称、价格、库存、适配信息、查询时间 | 未找到与系统失败必须区分；不自动发送卡片 |
| `product.get` | 来自搜索或近期上下文的真实引用 | `product_ref` | 完整商品事实、权益、卡片可用性 | 引用失效则重新搜索，不使用旧价格 |
| `product.send_card` | 商品真实、当前可售且有合理销售目的 | `product_ref`、会话引用、承接文本可选 | `queued_ref` 与最终发送状态 | queued 不等于 sent；失败后不说“已经发了” |
| `care_manual.search` | 已知品种、商品或养护主题之一 | 查询词、品种名、`product_ref` 可选 | `material_ref`、标题、匹配原因、发布和权益状态 | 匹配不确定时不随便发品种手册 |
| `material.search` | 已理解客户想解决的问题或关系目的 | 问题、品种、客户关系、资料目的 | 候选 `material_ref`、价值、适用和限制 | 不把所有“资料”请求都映射到同一张卡 |
| `material.send` | 已有真实资料引用，满足权益和重复发送条件 | `material_ref`、会话引用、发送目的 | `queued_ref` 与最终发送状态 | 无引用、权益未核实或客户拒绝时不执行 |
| `order.search` | 客户主动询问且身份范围明确 | `customer_ref`、客户主动提供手机号可选 | 脱敏订单列表和 `order_ref` | 缺手机号时自然索取；未找到不等于系统失败 |
| `order.get` | 已有当前客户的真实订单引用 | `customer_ref`、`order_ref` | 状态、商品摘要、付款、发货和物流可用字段 | 不返回无关地址；不把只读查询变成修改承诺 |
| `memory.record` | 信息值得跨轮使用且有来源事件 | 事实 / 承诺 / 纠正、证据事件、有效时间 | 候选状态、是否接受、冲突或拒绝原因 | 模型输出只是候选；动态业务状态必须来自工具 |
| `wakeup.schedule` | 有明确未来判断理由和取消条件 | 客户引用、时间范围、原因、检查项、取消条件 | `wakeup_ref`、计划时间和状态 | 不保存预写营销话术；新消息、退订或成交可取消 |
| `human.handoff` | 达到硬边界或人工更合适 | 客户引用、原因、事实摘要、已做动作、待办 | `handoff_ref` 与接管状态 | 未成功创建时不能声称人工已接手 |
| `capability.search` | Agent 不确定能力名称 | 当前目标、希望得到的结果 | 少量相关工具 / Skill 名称和短描述 | 不返回全部 Schema，不替 Agent 做销售路由 |

## 工具返回统一要求

- 查询结果区分 `found`、`not_found`、`invalid_arguments`、`temporarily_unavailable` 和 `forbidden`。
- 所有动态事实携带来源和查询时间；发送与写操作返回稳定动作引用。
- 写操作至少区分 `planned`、`queued`、`sent`、`failed`、`cancelled`。
- 商品、资料和订单分别使用稳定 `product_ref`、`material_ref`、`order_ref`，模型不能自己构造。
- 工具只返回完成当前判断需要的数据，详细内容继续按需读取。

## 第一版优先顺序

【建议草案】先开放只读和低风险能力，再开放真实动作：

1. `customer.get_context`、`product.search/get`、`care_manual.search`、`material.search`、`order.search/get`。
2. `product.send_card`、`material.send`，统一进入现有微信队列。
3. `memory.record`，只提交候选并经过现有证据验证。
4. `wakeup.schedule`，替代固定未购买 SOP 的预写话术。
5. `human.handoff` 与 `capability.search` 完成统一封装。

## 【请修改】你只需要重点审阅

- 工具名称是否符合你们业务人员的理解。
- 第一版是否还需要“活动查询、物流单独查询、售后工单”等独立工具。
- 资料、商品和唤醒写操作的权限是否需要进一步收紧。
