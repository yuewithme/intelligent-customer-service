# 04 工具清单与渐进式披露

工具负责提供真实能力，不负责规定销售流程。Agent 自主决定是否调用；系统负责参数、权限、幂等和执行状态。

## 双层工具描述规范

每个工具有两层说明：

1. `short_description`：始终可见，一到两句话，说明“什么时候用”和最重要的边界。
2. `full_instructions`：Agent 选择相关能力后才加载，包含完整参数、结果、失败和副作用。

短描述示例：

```text
product.search
客户明确选购，或已有需求和关键条件足以解释某类商品为什么适合时，查询真实商品、价格和适用场景。新好友、普通兰花话题和 Agent 单方面猜测商品有帮助，本身都不构成调用理由；信息充分时不必等待客户先说想买。
```

## 最终工具目录

| 工具 | `short_description` | 类型 | 当前基础 | 披露方式 |
| --- | --- | --- | --- | --- |
| `capability.search` | 不确定有哪些工具或经验能帮助当前任务时，搜索最相关能力。已经知道具体工具时不要调用。 | 只读 | 需要新增 | 始终可见 |
| `customer.get_context` | 当前判断需要客户历史、偏好、购买、承诺、待办或今日触达状态时读取证据化客户工作区。不要用它猜测动态价格和订单状态。 | 只读 | Memory 2.0 已有基础 | 每轮自动注入摘要，完整 Schema 按需 |
| `customer.tag` | 客户本轮亲口提供盆数、主要品种或足以判断 L1-L6 的稳定证据时，记录目录内标签。标签只辅助判断；两个已购标签禁止由模型写入。 | 证据化写入 | 复用现有客户标签目录和画像事件 | 标签相关时加载 |
| `knowledge.search` | 需要核实兰花品种、养护、病害或操作知识时查询专业知识库。不能用它查询实时商品和订单。 | 只读 | 现有兰花知识库与 RAG 已有 | 专业问题相关时加载 |
| `product.search` | 客户明确选购，或已有需求和关键条件足以解释适配理由时，查询真实商品、价格、库存和适配字段。新好友和普通养护聊天不默认调用；信息充分时可主动推荐。 | 只读 | 商品目录与有赞能力已有 | 完整 Schema 延迟加载 |
| `product.get` | 已有明确 `product_ref`，需要核实完整规格、权益或卡片信息时读取详情。不要用模糊名称调用。 | 只读 | 有赞 `get_product` 已有 | 由 `product.search` 结果引导加载 |
| `product.send_card` | 客户明确选择，或已根据其需求和关键条件形成有依据的主动推荐时，发送真实 `product_ref` 对应卡片。不能解释适配理由时不以卡片打断聊天。 | 写入 | 微信小程序卡片和队列已有 | 选择商品后才加载 |
| `care_manual.search` | 需要为具体品种、商品或养护主题查找已发布养护手册时使用。通用常识可直接回答时不必调用。 | 只读 | 养护手册库已有 | 相关养护 Skill 中披露 |
| `material.search` | 资料可能帮助当前问题、建立价值或形成后续触点时，搜索匹配资料及使用条件。不要把搜索等同于发送。 | 只读 | 陪伴资料与手册库部分已有 | 相关时加载 |
| `material.send` | 已能说明资料与客户需求的匹配、释放目的和后续推进时，发送真实 `material_ref`；客户索要本身不等于调用。不得绕过权益、重复发送和微信队列。 | 写入 | 资料卡片、图片和队列已有 | 搜索返回引用后加载 |
| `order.search` | 客户询问订单、付款、发货或物流时，按当前客户身份和客户主动提供的手机号查近期订单。不得按模糊姓名跨客户查询；查到已付款真实订单后自动记录微信已购。 | 只读并回写可信标签 | 有赞订单查询已有 | 订单场景加载 |
| `order.get` | 已有明确 `order_ref`，需要核实某笔订单详情时使用。查到已付款真实订单后自动记录微信已购；不得用于修改、退款或取消。 | 只读并回写可信标签 | 有赞单笔订单已有 | 由 `order.search` 引导加载 |
| `memory.record` | 当前对话产生了稳定客户事实、明确偏好、承诺、纠正或待办时，提交带证据的记忆候选。不要记录短暂寒暄和模型猜测。 | 写入候选 | Memory 2.0 已有候选、验证和合并 | 相关时加载 |
| `human.handoff` | 客户要求人工、申请优惠、需要授权写操作、重大售后或现有证据不足以安全处理时转人工，并携带摘要和未完成事项。 | 写入 | 人工接管与通知已有 | 始终可发现，完整 Schema 按需 |

## 完整工具说明

| 工具 | 使用前提 | 关键输入 | 关键输出 | 不使用 / 失败边界 |
| --- | --- | --- | --- | --- |
| `customer.get_context` | 已解析当前租户和客户身份 | `subject_ref`、当前任务摘要 | 当前事实、相关经历、工作状态、今日真实触达次数、最近触达主题、未知和证据 | 不返回无关隐私；检索失败时使用当前对话，不假装记得 |
| `customer.tag` | 客户本轮原话含有稳定事实，且标签存在于目录并允许 AI 写入 | 准确标签名、当前客户原话片段 | `recorded`、当前客户标签 | L1-L6 不由单个关键词决定；抖音已购、微信已购属于受保护标签，客户自述和模型推测都返回 `forbidden` |
| `knowledge.search` | 当前问题需要超出通用低风险常识的专业事实 | 具体知识问题、当前客户已知条件 | 有来源的知识答案、来源引用和查询状态 | 没有可靠资料时返回 `not_found`；不得扩写成疗效、一定养活或一定开花承诺 |
| `product.search` | 客户明确选购，或其需求、经验、环境、偏好等事实已经足以形成有理由的主动推荐；新好友身份和普通兰花话题不算前提 | 查询词、客户关键条件、数量上限 | `product_ref`、名称、价格、库存、适配信息、查询时间 | 若一个未知仍会明显改变推荐，先继续挖需；未找到与系统失败必须区分；不自动发送卡片 |
| `product.get` | 来自搜索或近期上下文的真实引用 | `product_ref` | 完整商品事实、权益、卡片可用性 | 引用失效则重新搜索，不使用旧价格 |
| `product.send_card` | 商品真实、当前可售，且客户已明确选择或推荐能由客户事实支持 | `product_ref`、会话引用、承接文本可选 | `queued_ref` 与最终发送状态 | 必须说明为什么适合；queued 不等于 sent；失败后不说“已经发了” |
| `care_manual.search` | 已知品种、商品或养护主题之一 | 查询词、品种名、`product_ref` 可选 | `material_ref`、标题、匹配原因、发布和权益状态 | 匹配不确定时不随便发品种手册 |
| `material.search` | 已理解客户想解决的问题或关系目的 | 问题、品种、客户关系、资料目的 | 候选 `material_ref`、价值、适用和限制 | 不把所有“资料”请求都映射到同一张卡 |
| `material.send` | 已有真实资料引用，且当前客户、需求、释放目的和后续动作足以说明为什么此刻值得发送；或作为不购买后的最终福利触点 | `material_ref`、会话引用、发送目的 | `queued_ref` 与最终发送状态 | 客户索要但基本信息和需求仍不清楚时，本轮先问一个相关关键点而不发送；无引用、权益未核实或通道不可发送时不执行 |
| `order.search` | 客户主动询问且身份范围明确 | `customer_ref`、客户主动提供手机号可选 | 脱敏订单列表、`order_ref`，已付款时可信写入微信已购 | 待付款、已关闭、未找到和系统失败都不形成已购标签；缺手机号时自然索取 |
| `order.get` | 已有当前客户的真实订单引用 | `customer_ref`、`order_ref` | 状态、商品摘要、付款、发货和物流可用字段，已付款时可信写入微信已购 | 不返回无关地址；待付款或已关闭不形成已购标签；不把只读查询变成修改承诺 |
| `memory.record` | 信息值得跨轮使用且有来源事件 | 事实 / 承诺 / 纠正、证据事件、有效时间 | 候选状态、是否接受、冲突或拒绝原因 | 模型输出只是候选；动态业务状态必须来自工具 |
| `human.handoff` | 达到硬边界、需要申请优惠或人工更合适 | 客户引用、原因、事实摘要、已做动作、待办 | `handoff_ref` 与接管状态 | 未成功创建时不能声称人工已接手或优惠已经申请成功 |
| `capability.search` | Agent 不确定能力名称 | 当前目标、希望得到的结果 | 少量相关工具 / Skill 名称和短描述 | 不返回全部 Schema，不替 Agent 做销售路由 |

## 工具返回统一要求

- 查询结果区分 `found`、`not_found`、`invalid_arguments`、`temporarily_unavailable` 和 `forbidden`。
- 所有动态事实携带来源和查询时间；发送与写操作返回稳定动作引用。
- 写操作至少区分 `planned`、`queued`、`sent`、`failed`、`cancelled`。
- 商品、资料和订单分别使用稳定 `product_ref`、`material_ref`、`order_ref`，模型不能自己构造。
- 工具只返回完成当前判断需要的数据，详细内容继续按需读取。
- 当前活动库尚未完整时，不创建虚假的活动查询结果。Agent 可以提出“帮您问问或申请看看”，再使用 `human.handoff` 并将原因标记为优惠申请；未来活动库完整后再新增真实活动查询工具。

## 直接替换版本的实施范围

新架构不按影子或灰度分批接管，但实现仍按依赖顺序完成并在一次替换前统一验证：

1. `customer.get_context`、`customer.tag`、`knowledge.search`、`product.search/get`、`care_manual.search`、`material.search`、`order.search/get`。
2. `product.send_card`、`material.send`，统一进入现有微信队列。
3. `memory.record`，只提交候选并经过现有证据验证。
4. `human.handoff` 与 `capability.search` 完成统一封装；优惠申请先复用人工接管，不等待活动库建设。

以上能力全部通过离线工具契约和真实队列状态验证后，主决策入口一次性替换；不存在只让部分真实客户使用新 Agent 的运行方式。
